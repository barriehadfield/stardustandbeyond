# CLAUDE.md — Stardust & Beyond

Static, image-first photo-archive website for **The Stardust** — a 1970s Durban
disco — and the friends who lived it, kept across four decades. Served as a
**static GitHub Pages site from the repo root**. Plain HTML/CSS/JS — no framework,
no runtime deps. Scaffolded from the `henridavies` template; content imported from
a Google-Docs export (see below).

Design: a **1970s disco** identity — deep-aubergine night ground, **gold** (`#f4b740`)
primary accent + **hot-magenta** (`#ff4fa3`) secondary, a soft dance-floor glow, a
serif display wordmark, image-first galleries on "raised" surfaces, and a full-screen
**swipe + pinch-zoom** lightbox. Tasteful retro — the photographs stay the star.

## Content origin

Content comes from a Google-Docs `.docx` export via **`scripts/import-docx.py`**
(a `.docx` is a zip: seven `sz=52` headings = the sections/tabs, each image's
`descr` alt-text = the photo caption, the first uncaptioned image under "The
Stardust" = the club `LEAD`; a photo may appear in more than one tab, exact
same-tab repeats are skipped; `Aydee`/`Adee` are normalised to `Adi`). **Image
names are content-stable (see "Filename stability" below):** an image whose bytes
already exist keeps its current filename even when a fresh export renumbers
everything, so file-keyed data (the people overrides) survives a re-import; only
genuinely new photos get new names. It copies each embedded image into
`source/images/<slug>/` and regenerates
`scripts/site-data.mjs` (preserving the hand-written `STARDUST_TEXT` /
`BOUDOIR_TEXT` intros). The raw `.docx` (and any earlier HTML export folder) are
**gitignored** (large, redundant with `source/images/`).

**Re-import after the doc changes:** download it as `.docx` into `source/`, then

```bash
python3 scripts/import-docx.py "source/Stardust and Beyond.docx"          # dry-run: prints per-tab counts
python3 scripts/import-docx.py "source/Stardust and Beyond.docx" --apply  # rewrites source/images + site-data.mjs
npm run optimize && npm run build
```

## Filename stability (why this matters for re-imports)

A fresh Google-Docs export **renumbers every embedded image** (`image1`, `image2`, …
in document order) - so the same photo comes back under a different name each export.
Because the site keys data by filename (`GALLERIES` items, and especially the people
**overrides** `Section | File`), a naive re-import would orphan all of it. Guard:

- **`source/image-names.json`** - a committed **byte→name manifest** (`sha1(image
  bytes) → base name`), the canonical record of every photo's stable filename. It is
  the audit trail and survives even a wiped `source/images/`.
- On import, `import-docx.py` builds a `hash → base` map (seeded from `source/images/`,
  then the manifest wins), and gives each incoming image the **existing name for its
  bytes**; only genuinely new photos get a fresh name. On `--apply` it re-writes the
  manifest as a union (old ∪ this export), so names are never lost. Verified: a re-export
  reused **1182/1182** names.
- Consequence: unchanged photos keep their filenames across exports → overrides and any
  file-keyed data stay valid. A photo whose **bytes change** (re-scan/re-crop) counts as
  new and gets a new name; its old override then dangles (harmless - reported, re-tag it).
- `image-names.json` is committed (not gitignored). Don't hand-edit it; the importer owns it.

## Mental model

```
DATA (edit this)              →  BUILD (scripts)     →  OUTPUT (committed, don't hand-edit)
scripts/site-data.mjs             npm run build          index.html, the-stardust.html, …
source/images/<slug>/*            npm run optimize       public/images/<slug>/*
```

- **`scripts/site-data.mjs`** — single source of truth: `SITE`, `SOCIAL`
  (`instagram` / `bluesky` / `whatsapp`; empty ones are omitted), `LEAD` (the club
  photo), `SECTIONS` (the tab registry), the `STARDUST_TEXT` / `BOUDOIR_TEXT` intros,
  and one gallery array per section, aggregated into `GALLERIES`. Each item is
  `{ file, title? }`; `title` is the caption. Array order = display order.
- **`source/images/`** — full-resolution originals (archive), one folder per section.
- **`public/images/`** — web derivatives. **Generated — do not edit by hand.**
- **`*.html` at repo root** — the pages. **Generated by `scripts/build-pages.mjs`.**
- **`source/people.md`** — the **People** master index (hand-edited, allow-list +
  per-photo overrides). Single source of truth for the People tab; the importer
  never touches it. See **People index** below.
- **`css/style.css`, `js/site.js`, `js/gallery.js`, `js/person.js`** — hand-written,
  the real site assets. `js/gallery.js` holds the shared masonry + PhotoSwipe init
  used by both `site.js` (section pages) and `js/person.js` (the People detail page).

## Pages & sections

`index.html` (landing — club hero + section cards) and one page per tab:
`the-stardust.html` · `the-boudoir.html` · `steven.html` · `70s.html` · `80s.html`
· `90s.html` · `2000.html`, plus `people.html` (the People index) and `person.html`
(the JS-driven per-person view). Nav, home "rooms" grid, and page builders are all
driven by the `SECTIONS` array (People is appended to the nav separately; it is not
a photo section). `LEAD` (`the-stardust/image861`, the uncaptioned club photo) is
the site's hero on the home page and a glowing lead figure atop the Stardust page.
The Stardust page opens with `STARDUST_TEXT`, the Boudoir page with `BOUDOIR_TEXT`
(section intros are wired via `SECTION_TEXT` in `build-pages.mjs`). Every page also
carries a WhatsApp "Join the group" nav item and a footer button, from
`SOCIAL.whatsapp`.

## People index

The **People** tab is built from `source/people.md` (the master index), matched
against the photo captions by `scripts/people.mjs` during `npm run build`.

- **`source/people.md`** — hand-edited, editable on GitHub. Two markdown tables:
  a **Roster** (`Name | Aliases | Primary`) and per-photo **Overrides**
  (`Section | File | People`). It is an **allow-list** — only rostered people become
  links, so caption noise (place/event names) is ignored automatically. `Aliases`
  (`;`-separated) merge spelling variants/nicknames into one person. `Primary` marks a
  **deliberate** default person for a shared first name — used **sparingly** (currently
  only the two central figures **Steven Roche** and **Patrick Brill**, whom a lone
  "Steven"/"Patrick" always means); leave it blank for everyone else so bare mentions
  resolve by evidence, not a guess (see matching below). An override row gives the
  definitive people for one photo (replaces auto-matching). **The importer never rewrites
  this file**, so corrections survive a re-import.
- **Bare names resolve by evidence, not guessing** (the doc now carries surnames, so a
  bare first name is meaningful). For a shared first name `computePeople`: (a) prefers a
  **surname-less** roster person (someone known *only* by that first name — bare "Karen");
  else (b) picks the candidate who most **co-occurs with the photo's confidently-identified
  people, within the same section/decade** (overrides are the training signal); else (c)
  the deliberate `Primary`; else (d) leaves it **unresolved** rather than mis-attributing.
  The report lists every co-occurrence resolution to spot-check, everything still
  unresolved, and **people without a surname** with who they co-occur with (to help
  surname them).
- **`scripts/people.mjs`** — `parsePeopleMd()` + `computePeople()` (the matcher) +
  a `--draft` mode (`npm run people:draft`) that lists candidate names from captions
  to seed the roster.
- **Build outputs:** `public/people.json` (per-person photos + dims, consumed by
  `js/person.js`), `people.html` (static A-Z index by first name), `person.html`
  (JS shell; `person.html?p=<slug>` shows one person's photos grouped by section),
  and `scripts/people-report.md` (**gitignored, review-only**) listing unresolved
  ambiguous photos (with live image URLs), shared first names, and unmatched tokens.
- **Curation loop:** `npm run build`, read `scripts/people-report.md`, then resolve
  each ambiguous/unmatched case by editing `source/people.md` (add an override, add an
  alias, or add a missing person) and rebuild — or, far faster, use the **corrections
  console → "Needs a name"** filter (below) and apply its export.

### How a caption is matched to people (`computePeople`)

The doc names people in free prose - full name on first mention, first name after,
surname re-added when ambiguous - so matching is a pipeline, not a lookup:

1. **Tokenise into mentions** (`mentions()`): split the caption on list connectors
   **and sentence punctuation** (`, . ; : & / and with aka as`); from each fragment
   take the leading run of Capitalised words, keeping lowercase **surname particles**
   (`de van von du der di la le mc mac`) when a capitalised word follows (so
   "Jean de Cruz" / "Michael van Rensburg" stay whole); strip a trailing possessive
   and stray punctuation; drop leading/trailing **title/place stopwords** (`Miss Mr
   The South Africa Natal Stardust …`). The sentence-punctuation split matters: without
   it "Sandy Bay. Henry Davies" swallows the real name.
2. **Resolve each mention** (`resolveMention`), longest-first:
   exact **full name / alias** (up to 3 words) → **unique first name** → a shared first
   name with exactly one **surname-less** candidate → that person → else it is an
   **ambiguous shared first name** (deferred to pass 2) → else **unmatched** (not in the
   roster → ignored by the allow-list, tallied in the report).
3. **Overrides win:** a photo with an override row skips steps 1-2 and uses the listed
   people verbatim (names resolved via the roster/aliases).
4. **Resolve the ambiguous ones by evidence** (pass 2): score each candidate by how often
   it **co-occurs with the photo's confidently-resolved people, weighted to the same
   section/decade** (3× same-section, 1× global); pick the top score; else the deliberate
   `Primary` (kept only for Steven Roche / Patrick Brill); else **leave it unresolved**
   (do not guess). Confident attributions (full names, unique firsts, overrides) are the
   only training signal - so **overrides both fix a photo and teach the resolver**.
5. **Report** (`scripts/people-report.md`): co-occurrence resolutions (spot-check
   these), still-unresolved, shared first names (how each resolved), **people without a
   surname** + their top co-occurring people, and unmatched tokens (candidate new people
   vs place/event noise).

**On a further docx change (the standard workflow):**
1. Drop the new `.docx` in `source/`, then `import-docx.py --apply` → `npm run optimize`
   → `npm run build`. Filenames stay stable (manifest), so existing overrides and
   `Primary`/alias choices keep working; only genuinely-new photos get new names.
2. Read `scripts/people-report.md`. **Add genuinely-new people** to the roster — a new
   person who shares a first name with an existing one is otherwise **absorbed** into
   them (watch the "unmatched" and co-occurrence lists for this), and **surname the
   surname-less** where the doc now reveals a surname (rename, e.g. `Arthur` →
   `Arthur Garrod`, which keeps their photos and auto-aliases the bare name).
3. Resolve the leftover ambiguous photos via the **corrections console → "Needs a name"**
   filter (below), then apply its export with `apply-corrections.mjs`. Aim for **0
   unresolved** in the report.

### Corrections console (local tool)

A browser tool for gathering fixes without hand-editing markdown. It's local-only
(`corrections.html` carries `noindex`, isn't linked from the site, and its data file
is gitignored).

- `corrections.html` + `js/corrections.js` — the UI. **Photos** tab: browse/edit who's
  in each shot (→ overrides), with filters incl. **"Needs a name"** (the ambiguous/
  unresolved photos) that shows each thumbnail with one-click candidate buttons — the
  surnamed options **plus a "just \<First\>" button** to file someone under their bare
  first name when the surname is unknown, plus **nobody**. **People & names** tab: rename
  / merge / remove / add roster entries (each links to that person's photos). **Export**
  tab: produces the corrections JSON. Work persists in `localStorage` (⚠ incognito clears
  it on close — Export before closing). The page dynamically imports its script with a
  cache-busting query so a stale module can't mask changes.
- `public/editor-data.json` — the tool's data (photo→people incl. `needs` candidates,
  roster, sections), written by `scripts/build-editor.mjs` on every `npm run build` (or
  `npm run editor`). Gitignored.
- **Round trip:** open `http://localhost:8000/corrections.html` (after `npm run dev`),
  make fixes, Export → **Copy** or **Download** `stardust-corrections.json`. Apply with
  `node scripts/apply-corrections.mjs <file>` (dry-run) then `--apply` — it rewrites the
  Roster + Overrides tables in `source/people.md` in place, handling `overrides` and
  roster `rename` / `merge` / `delete` / `add` / `aliasAdd`. Then `npm run build`. The
  exported `source/stardust-corrections*.json` files are gitignored (transient).

## Commands

```bash
npm install        # once — installs sharp (build-time only, a devDependency)
npm run optimize   # source/images/**  ->  public/images/**  (after adding/replacing originals)
npm run build      # regenerate all root *.html + the People index from build-pages.mjs
npm run people:draft # print candidate names from captions (to seed source/people.md)
npm run editor     # (re)write public/editor-data.json for the corrections console
npm run people:apply # node scripts/apply-corrections.mjs — apply an exported corrections file
npm run favicon    # source/images/site/favicon.svg -> public/images/site/{favicon.svg,icon-32,icon-180}
npm run dev        # no-cache static server at http://localhost:8000
```

**Serve with `npm run dev`, not `python3 -m http.server`** — `scripts/dev-serve.py`
sends `no-store` so refreshes always show freshly built files. If port 8000 is busy,
run `python3 scripts/dev-serve.py <port> .` directly.

No test suite. "Verify" = build, serve, screenshot with headless Chrome. Headless
Chrome enforces a ~500px minimum viewport — use `--window-size=600,…` for mobile.

## Image pipeline (`scripts/optimize-images.mjs`)

For every original in `source/images/<slug>/` it emits four files into the matching
`public/images/<slug>/` folder: `<name>.webp` / `<name>.jpg` (full, max edge 2000px)
and `<name>-thumb.webp` / `<name>-thumb.jpg` (max edge 800px). Section folders are the
`SUBDIRS` array (the seven slugs + `site`). EXIF orientation respected; originals never modified.

## Adding / changing content

- **Bulk update from the doc** (many photos/captions, moves between tabs, a new tab):
  re-run `scripts/import-docx.py` — see **Content origin** above. It rewrites
  `source/images/` and `site-data.mjs` wholesale.
- **Single new photo (by hand):** drop the original into `source/images/<slug>/`,
  `npm run optimize`, add `{ file: "name", title: "caption" }` to the matching array
  in `site-data.mjs`, `npm run build`.
- **Caption / order / blurb / tagline:** edit `site-data.mjs`, `npm run build`.
  (The home hero tagline is in `buildHome()` in `build-pages.mjs`.)
- **People (names, merges, who's in a photo):** edit `source/people.md`, `npm run
  build`. See **People index** above.
- **New section (tab):** add a slug folder under `source/images/`, add it to
  `SUBDIRS` in `optimize-images.mjs`, add an entry to `SECTIONS` + a gallery array +
  a `GALLERIES` key in `site-data.mjs` (also to `VARMAP`/`BLURB` in
  `import-docx.py` if it should survive re-import), optimize, build.

## Conventions & gotchas

- **Relative asset paths** only (`public/images/…`, `css/…`) — never root-absolute `/…`.
- **No em-dashes** in visible copy (user preference); **UK spelling**. The importer
  already replaced dashes in captions with hyphens.
- `.nojekyll` is present so Pages serves files as-is.
- Palette + glow are CSS custom properties at the top of `style.css` — retune globally there.
- Lightbox is PhotoSwipe v5, vendored at `js/vendor/photoswipe/` (no CDN). Tiles carry
  `data-pswp-width`/`data-pswp-height` (full-image dims) and `data-title` (caption).
